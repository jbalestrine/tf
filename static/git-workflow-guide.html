Update and push your app: essentials

Save your edits first. These actions run in the local MasterChief repository. Each button selects a command below; check its preview, choose Run command, confirm when prompted, and check the output before continuing.

  1. Check your branch and changes: run git status. “Up to date” only compares commits; your edited and new files may still be uncommitted.
  2. Stage changes: run git add -A to stage all tracked edits and deletions and non-ignored new files. To include only certain files, use Stage a selected path instead.
  3. Review what will be committed: run git status, then git diff --staged to inspect tracked staged content. Review new files too, and check for credentials or private data.
  4. Commit: select Commit staged files, enter a meaningful message, and run git commit -m "Describe your changes". The commit includes every staged change.
  5. Push: run git push if your branch already has an upstream. Otherwise choose Push branch and set upstream and enter your branch name. Push sends commits, not unstaged or uncommitted edits.

Important: git add -A stages changes across the entire repository, including deletions and files you might not intend to publish. Ignored untracked files are not included. Previously staged files are included in the commit too. If you want only certain files, stage them individually and review the complete staged set before committing. A commit is local until pushed; pushing does not merge a pull request.

Safety and branches

  • Check status, staged changes, branch tracking and remote destinations before switching or pushing.
  • Branches are references, not separate app folders. A deleted remote branch does not delete the local branch.
  • Verify work is merged or backed up before branch cleanup. Squash merges may make safe deletion refuse.
  • Ignore rules do not protect already-tracked files. Review private data and credentials before staging or pushing.
  • Branches are pointers to commits, not backups. Keep both local and remote branches unless cleanup is intentional; GitHub repository settings may automatically delete merged remote branches. After a confirmed merge, fetch and create the next feature branch from the updated base.

Recovery and caveats

  • A commit includes only staged changes. Use git add -A to stage all changes or stage selected paths, then review git status and git diff --staged before committing. Push sends commits, not unsaved or uncommitted edits.
  • Inspect pending changes before switching or discarding. Reflog can help locate commits but is not a backup.
  • Revert creates a new commit; merge commits require special handling. Reverting does not remove secrets from history.
  • Resolve and stage conflicts before continuing a merge or rebase. Aborting can discard progress.
  • Reset hard, force-delete and force-push can discard work or rewrite history. Verify targets and backups first.

Command reference

Inspect with git status, git branch -vv, git remote -v, git diff and git diff --staged. Use git reflog and git show --stat <commit> to investigate prior work.

Prepare with git fetch origin and git switch -c <name> origin/Masterchief4; then stage, review, commit, push and create a pull request. Replace placeholders and check the target branch.
